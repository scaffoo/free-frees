  I want to build a new web-first generic card game platform from scratch.

  Goal:
  Create a hosted web app where card games are defined in a JSON/YAML-like declarative format, then playable in the browser by humans and bots. Start with two implemented games:
  1. Klondike Solitaire, traditional draw-3.
  2. Go Fish, 2-player, playable human vs bot or human vs human.

  Use a modern architecture and stack:
  - Frontend: React + TypeScript + Vite.
  - UI styling: Tailwind CSS, with a clean game-table UI.
  - Backend: Node.js + TypeScript.
  - Server framework: Fastify or Express; choose one and explain briefly.
  - Realtime multiplayer: WebSockets, preferably Socket.IO or native ws; choose one and explain briefly.
  - Database: PostgreSQL.
  - ORM/query layer: Prisma.
  - Auth: email/password login with secure password hashing and sessions/JWTs.
  - Runtime target: container-friendly, deployable later to Fly.io.
  - Monorepo package manager: pnpm.
  - Testing: Vitest for shared logic; backend tests where useful.
  - Avoid webpack; use Vite and current tooling.

  Core requirements:
  - Multi-user accounts with login/logout/register.
  - Multiple hosted game rooms at the same time.
  - Users can create games, list open games, join games, leave games, and resume games.
  - Game rooms support spectators later, but this can be designed only, not fully implemented initially.
  - Server is authoritative. Clients must not decide legal moves.
  - Game state should be persisted or event-sourced enough that a room can survive refresh/reconnect.
  - Bots should use the same move interface as human players.

  Declarative game definition language:
  Design a JSON/YAML-like format for defining card games. It should be readable and schema-validatable. Do not use a Lisp-like DSL.
  The language should eventually support:
  - Standard and custom decks.
  - Card attributes: rank, suit, color, value, joker/wildcard flags.
  - Zones/locations: stock, discard, tableau, foundation, hand, trick, meld area, pot, community cards, etc.
  - Visibility rules: public, owner-only, hidden, team-only, derived/known information.
  - Turn structure: phases, steps, choices, automatic actions, end conditions.
  - Legal move generation.
  - Scoring.
  - Multi-round games.
  - Bots.
  - Hidden information.
  - Common card game patterns needed for bridge, rummy, poker, trick-taking games, shedding games, fishing games, and solitaire.
  - Higher-level primitives where appropriate, such as deal, draw, discard, move, ask-rank, reveal, shuffle, compare-rank, build-up/down, alternate-color, same-suit, meld-set, meld-run, trick-winner, betting-
  round.

  Important design principle:
  Separate the authoring format from the engine runtime:
  YAML/JSON definition -> validation -> compiled typed GameDefinition/Rules AST -> engine runtime -> legal moves -> state transition.

  Initial implementation scope:
  Build the platform skeleton and implement enough of the rule system to support Klondike draw-3 and Go Fish.

  Klondike draw-3 requirements:
  - Single-player room.
  - Standard 52-card deck.
  - 7 tableau columns with traditional deal.
  - Stock, waste, 4 foundations.
  - Draw 3 from stock to waste.
  - Recycle waste back to stock when stock is empty.
  - Tableau building: descending rank, alternating color.
  - Foundations build ascending by suit from Ace to King.
  - Face-down tableau cards flip when uncovered.
  - Win condition: all cards in foundations.
  - Legal moves generated by server.
  - Browser UI supports clicking/selecting legal moves.

  Go Fish requirements:
  - 2 players.
  - Human vs human or human vs bot.
  - Standard 52-card deck.
  - Deal appropriate initial hands, use a stock pile.
  - On turn, current player asks another player for a rank they have.
  - If target has matching cards, transfer all matching cards and current player continues.
  - If not, current player draws from stock.
  - If drawn card matches requested rank, current player continues; otherwise turn passes.
  - Completed books/sets of 4 are laid down.
  - Game ends when all books are complete or no cards remain as appropriate.
  - Winner determined by most books.
  - Hidden hands: each player sees only their own hand.
  - Bot can make legal random choices.

  Architecture expectations:
  - Create clear packages:
    - apps/web: React/Vite frontend.
    - apps/server: backend HTTP/WebSocket server.
    - packages/engine: generic card engine, rules compiler/runtime, bots.
    - packages/shared: shared types and validation schemas.
  - Use TypeScript throughout.
  - Use Zod or JSON Schema for definition validation. Choose one.
  - Define stable IDs for cards, zones, players, games, rooms, and moves.
  - Legal moves should be serializable objects with IDs, labels, type, and payload.
  - State transitions should be deterministic except for explicit random actions, with RNG handled server-side.
  - Include a basic event log model for game actions.
  - Design for future deployment to Fly.io, but local development first.

  Deliverables for the first pass:
  1. Scaffold the monorepo.
  2. Implement the generic engine primitives needed by Klondike and Go Fish.
  3. Add declarative definitions for Klondike and Go Fish.
  4. Add server APIs:
     - register/login/logout/me
     - list game definitions
     - create room
     - list rooms
     - join room
     - leave room
     - get room state
     - submit move
  5. Add WebSocket room updates.
  6. Add simple React UI:
     - auth screens
     - lobby
     - room/game screen
     - Klondike board
     - Go Fish hand/table view
  7. Add a random bot for Go Fish.
  8. Add tests for the engine legal move generation and state transitions.
  9. Provide local run instructions.

  - Keep the initial implementation focused but architecturally clean.
